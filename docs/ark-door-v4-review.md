# Door v4: offline Modify/Debug review

This new development contract fixes the task-level missing-cell ambiguity. It
does not change prior freezes, original candidates, original oracle or scores.
The historical repair001 JS static FAIL is retained as an assessment with a
wording ambiguity, not established proof that the old task was violated.

Both arms receive identical business/host rules. Missing target entities finish
normally; existing targets require door.open. An open door does not require keys;
a closed door requires player.keys. Required missing cells raise InvalidEntity.
Business effects follow required-value validation. An error rolls back the whole
tick, including earlier Open effects; attempted-effect audit entries may remain.
Ordinary read still returns option and does not itself throw on none. There is
no exact safe-query order, syntax or host-call-count equality requirement.

Modify receives a correct cost=1 starter and changes its one cost binding to 2.
Debug receives one reversed comparison (IR le, JS <=), with cost=1 unchanged.
The starter files are independent public data, in the native syntax of each arm.
Public request construction never loads the private oracle, reference answer,
opposing starter, old model candidate or repair feedback. Full review metadata
contains both arms and private oracles and must NEVER be sent to the model.

New diagnostics are four scenarios per task, seeds 1 and 123: missing open with
both targets present; missing player before missing open; missing door before
missing keys; successful Open followed in the same tick by an Open on a second
door with missing open, requiring complete rollback. Expectations are authored
from the contract, not generated by a runtime, reference or model result.
The unchanged legacy26 selects the existing task-specific oracle by hash.
Existing scenarios 10/11 provide open-door/missing-keys and closed-door/missing-
keys controls. Legacy26 and diagnostic8 results must be reported separately.
All candidate gameplay is currently NOTRUN. Trusted-engine verification of
authored controls cannot count as model gameplay or full contract coverage.
Tests check both the authored IR control and the existing bounded ctx mock,
including their replays. Public JS starter syntax is checked without evaluation.
Player/door alias and complete source-path/effect/rollback coverage remain
NOT_CHECKED. This is post-observation development, not a holdout or AI advantage.

The proposed four independent sessions run Modify IR then JS, Debug JS then IR.
Each has one attempt, zero repairs/tools, max output4096 tokens, max source16384
UTF-8 bytes and input24000 byte+overhead units. No input padding, automatic retry,
paid fallback or exact-token-equality claim. Keep actual usage/failures/NOTRUN.
The intended model is deepseek-v4-1-flash-260910 at the existing Plan-only route;
this frozen request is not availability, provider-route or speed attestation.

All host, worker, runner and container implementations are unchanged. No engine,
TS, Vitric, service or product expansion. Old source/history hashes are bound.
The freeze also binds the v4 constructor, tests, starters, diagnostic data and
this review note. Both send() and execute_candidate() unconditionally refuse;
there is no enable flag, credential reader, model transport or execution entry.
