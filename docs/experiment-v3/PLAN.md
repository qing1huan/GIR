## 1. 问题、边界和已有证据

研究问题：**当 AI 是主要开发者时，改变它操作代码的接口、程序的语义表示以及执行和验证机制，能否提高游戏逻辑的开发与持续维护效率、可靠性？** 可以得到“无收益”“工具成本抵消收益”或“证据不足”的结论；不以证明 IR 优势为目标。

保留 Headless、共享运行语义、游戏逻辑、压力测试，以及 Create / Modify / Debug。当前传统代码载体维持 JS。暂缓 Vitric 接入、Unity / Godot / UE、图形编辑器及产品平台建设。旧 Vitric 公平基线未取得，不把现有 JS callback 命名为旧 Vitric 基线。不为覆盖率临时增加玩法专用原语。

| 已有工作 | v3.0 中的用途 | 不能支持的结论 |
|---|---|---|
| `headless_v01`、`ark_eval/host.py`、确定性事务/回放/oracle | 三组共享的工程地基，维持同一行为语义 | 工程测试通过不是 AI 优势，也不是通用游戏表达能力证明 |
| `headless_v01/editing.py` | C 组已有 `query_nodes`、依赖查询、draft、validate/commit/rollback 的复用候选 | 尚未形成与 A/B 匹配的受测 Agent 工具接口；构造器及 evaluate 会接触 runtime，不能直接在宿主处理不可信候选 |
| 历史 Door v4：4 次生成、136 个固定用例观察通过 | 开发集、收集/隔离工程经验 | 单模块、2 类改动、每臂一次生成，不是 holdout 或三组研究 |
| 当前 Pilot24：6 任务 × 2 表示 × 2 次生成 | **无反馈、两表示的探索性基线**；按原规则收尾 | 没有强分析工具或语义编辑交互，不能重标为 A/B/C；不能评估多轮维护 |

冻结对象包括运行时语义、ABI、权限边界、回放、IPC 资源上限、现有候选/材料/测试及 oracle。后续仅新增薄适配层；凡需改变上述对象，先提交具体 diff、影响分析和新版本方案，不在旧冻结上补丁式覆盖。安全修复可以阻断后续实验，但必须版本化并说明受影响证据，不静默改变实验条件。

## 2. A/B/C 的可操作定义

| 项目 | A：代码 + 强分析 | B：代码 + 语义接口 | C：GameIR + 匹配接口/验证 |
|---|---|---|---|
| 受测可编辑工件 | 原生 JS 文件 | **与 A 相同的 JS 文件** | 语义等价的 GameIR |
| 观察接口 | 文件/范围读取、符号、定义/引用、诊断、AST/读写影响查询 | A 的全部事实，经统一语义查询包装；保留原文读取 | 对应节点/定义/依赖/诊断/读写影响查询，精度标记可比较 |
| 编辑接口 | 常规文本补丁和原生语言服务重构，修订校验、预览、原子提交/撤销 | 带稳定选择器、前置条件和影响范围的语义编辑事务；输出仍是 JS | 对应的节点/表达式/子树编辑事务；输出仍是 GameIR |
| 执行 | 原生 JS callback → 共享 HostRuntime | 与 A 完全相同 | 冻结 IR 编译/解释 → 相同事务与世界语义 |
| 验证 | 语法/分析诊断、同一公开测试与隐藏 oracle | 与 A 同一分析器和规则，不增添私有答案 | 匹配的公开反馈；IR 固有类型/结构检查另记，不当作无成本赠送信息 |
| 最小缺口 | 面向受测 Agent 的强分析工具会话、修订编辑及统一计费 | A 上增加查询/编辑薄封装、稳定选择器和可追溯事务 | 复用 SemanticEditor 思路，但须提供不可信输入隔离、统一 Agent 协议、匹配反馈与审计 |

**运行时 `ctx.exists/read/require/sub/write/emit` 是游戏程序执行时的能力，不是 Agent 查询或编辑源码的接口。** 三组都可使用这些共享业务能力；B/C 的变量是开发过程中 Agent 的操作接口。不能把现有 ctx API 已存在写成 B 已实现。

A 必须有正常可用的现代代码分析，不能只给 grep 或全文件字符串替换。A/B 必须调用同一个分析事实后端；B 不得额外内置任务解法、目标补丁或隐藏测试。C 查询的 `conservative/unknown` 精度须如实输出，不能把保守依赖当作精确证明。所有组均保留原文/原节点查看和通用表达式替换，不能把 C 限制成预制玩法按钮。

## 3. 最小工具接入，不迁移语言

JS 语法准入继续复用 `CandidateParserBackend` / `candidate_parser.mjs`。该解析器使用 `vm.SourceTextModule` 解析而不求值，可检查语法、导入及导出；它不是符号/引用/语义分析服务。

A/B 的最小强分析候选是成熟的 TypeScript Language Service，以 `allowJs` 管理 JS，并提供冻结的 ctx 声明和相同诊断配置。官方资料支持语言服务提供按需语法/语义诊断以及 host 管理文件上下文；`allowJs` 接纳 JS。这里是接入方案，未声称依赖已安装、版本已锁定或 ctx 读写关系能由语言服务自动证明。[Language Service API](https://github.com/microsoft/TypeScript/wiki/Using-the-Language-Service-API)；[allowJs](https://www.typescriptlang.org/tsconfig/allowJs.html)（查阅 2026-10-11）。

下一工程阶段先盘点现有依赖，再锁定本地可用的一个版本；使用只包含公开源码、公开声明的内存 host，禁用自动下载类型、插件、任意路径解析和网络。ctx 字段读写/控制流摘要用小型、可审查的 AST 适配器补齐，A/B 共用，无法推断时返回 unknown。不得自研整个语言服务器。B 只增加通用选择器和事务包装，不复制一套编译器。

现有 `SemanticEditor` 面向含 `nodes/connections` 的语义文档；Pilot24 的 IR 是含 `handlers` 的 Core JSON，不能直接当作同一输入接口。最小 C 原型保持当前 Core 序列化/执行语义，只对 handler 表达式提供修订绑定的路径选择器和薄事务包装，复用既有校验/提交设计；不把旧候选自动提升、改写成另一种 IR，也不声称 SemanticEditor 已可直接承载本批数据。若薄适配无法做到，应报告结构兼容缺口，不能借 v3.0 改造架构。

借用 TS 的分析工具不等于把受测 JS 迁移成 TS。若实际能力要求 TS 或 C#，先报告迁移原因与成本：两臂 starter/公开声明重写、转译或 CLR 执行链、源位置映射、隔离/运行语义复验、旧数据不可直接合并的代价。当前方案无需这项迁移，也未授权。

## 5. 对照、反馈和预算

正式实验的每个配对单位是一个任务链。一个链依序含理解测量、Create、Modify-1、Modify-2、Debug；每步隐藏验收都包含此前保留行为。三组从相同空业务入口/等价已验证初态开始；修改时各组继续自己的上一版，记录持续退化。前一步失败则该链后续标记 `NOTRUN_DEPENDENCY`，分母保留为整链失败，不给失败组注入参考解。另设“共同正确 starter”的配对诊断任务可区分工具能力与累计退化；与主链分开报告，不填补主链成绩。

正式材料在新调用前一次性冻结以下项目；未满足任一项不得开测：

1. 同一受测模型、Plan 路由、模型标识、采样参数和会话保留策略；Codex 做工程，方舟做受测模型。只用已有 Plan，付费回退/升级/重置卡均为 0。历史批次标识为 `deepseek-v4-1-flash-260910`；后续模型可用性或许可变化只能阻断，不可暗换模型/按量接口。
2. 同一任务需求、世界、外部行为语义、步骤顺序、种子、错误码与事务回滚约定。三组材料包含同等必要信息和示例；工具文档按功能对应，差异逐项登记。不通过删去某组必要说明或 padding 制造 token 相等。
3. A/B 使用逐字相同 JS 初态、声明和分析后端；C 初态与之在独立人工 oracle 上语义等价。Create 给同等空业务入口；所有参考解、私有测试、目标补丁不进入模型上下文、工具目录或诊断回复。
4. 公开测试和可见反馈预先固定，三组具有相同测试调用次数、粒度和上限。隐藏主 oracle 仅终局评分，不反馈答案。编译/类型检查的固有差别单列；共同反馈层以错误类别/公开位置/公开断言为单位，不向某一组泄漏额外因果解释。安全准入始终启用。
5. 每个开发步骤拟定相同上限：初次提交 + 最多 1 次修复，最多 2 份可评分工件，最多 6 次工具操作，最多 1 次公开测试反馈；工具/反馈内容同样计入模型输入。模型与工具交互可有最多 8 次模型请求/步骤、每次输出最多 4096 tokens、步骤累计输入+输出最多 32768 tokens，所有思考/缓存字段按服务账单口径另列。尝试次数按提交工件而非 HTTP 次数计，禁止自动重试或把未知请求当零消耗。
6. 上述是**未来协议候选上限，不是新增调用授权**。开测前必须验证与模型版本相符的 tokenizer/保守 token 上界，使每次请求能预留剩余输入与输出预算。现有 `UTF-8 bytes + overhead` 不是真实 token 上界；若无法验证，则严格 token 匹配状态为 BLOCKED，只能另行审批一个明确标注为宽松预算的探索协议，不暗称严格公平。成本看实际 usage；上限相同不要求实际用量相同。
7. 所有模型请求、工具操作、隐含展开/重试、失败、超时、未运行均逐项记录。工具输出长度预限并计入输入；语义操作的内部 AST 查询/重写次数、CPU/墙钟、峰值内存另计，防止一个语义调用无限打包工作。A/B/C 使用相同时间与资源上限；启动预热策略相同。
8. 组顺序按任务链平衡，生成重复用全新会话；链内保持预先规定历史，跨组和重复不共享解答。模型身份或服务版本漂移即暂停，不与旧批次无标签合并。

新实验必须另备“任务链数 × 组数 × 重复数 × 步骤数 × 请求上限”的总账及最坏 token 数，并得到独立预算批准。当前已用 24 槽采集额度不能挪为三组调用。

## 7. 能归因什么，最少需要哪些消融

A↔B 检验在相同 JS、分析事实与执行器下，语义操作界面的增量效果。B↔C 同时包含表示、编辑粒度、内在类型约束和执行验证机制变化；它是组合方案对照，不能单独归因于 IR。A↔C 是整个开发环境的净效果。三组并非三个因素的完整析因实验。

最小消融在正式结果前登记，先做无模型的机械一致性检查；未来若要模型消融必须额外申请预算：

- **B-query-only**：保留 B 的结构化查询，编辑退回 A 的常规编辑；与 B 匹配事实和预算，区分查询呈现与语义编辑事务的作用。
- **B/C common-feedback**：只向模型暴露配对的公共诊断类别/公共测试反馈，私有检查仍执行但不额外提示；与主比较区分诊断呈现效应。不能为了消融禁用安全隔离或改变实际评分。

这些消融仍不完全分离 IR 表示与执行机制。若要声称纯表示效应，必须有保持执行/验证能力相同的另一个受控设计；本计划不为此现在重写运行时。先报告组合效果和剩余混杂。

## 8. 成功标准与停止规则（只适用于未来新数据）

以下门槛在 v3.0 文档发布时固定，不追溯套到已见的 24 槽上。材料/样本/统计脚本与数值预算仍须在新调用前独立封存；门槛只能在新版本、未观察该版结果之前调整。

**可行性门**：M1 的查询事实对齐、修订拒绝、原子回滚、公开/私有信息边界和审计全部通过；全部运行语义回归保持通过；无新增模型调用。未通过只修工程，不做效果研究。

**探索门**：正式三组先做预先登记的小样本可行性 pilot，报告配对点估计和不确定性，不称显著优势。预先纳入的新任务必须覆盖 Create/Modify/Debug 和至少三类业务机制。全部通过/全部失败或任务过易/过难属于天花板/地板证据，不能据此追加“有利题目”。最多一次预先批准的 pilot；是否进入确认研究依据完整结果和可检验性，不自动扩样。

**确认门**：以任务链为聚类单位，重复生成先在链内平均；整条链保留，不能把用例或重复源码当独立样本。主比较是 B−A 和 C−A，C−B 是预登记次比较。成功路线提前选为“可靠性不劣且成本更低”，不在出结果后改成任一指标显著就赢：

- 整链终局成功率差的同时置信下界 ≥ −5 个百分点；保留行为回归率差的同时上界 ≤ +5 个百分点。
- 在所有分配任务链上计算每个成功链的模型总 token 成本：`全部链实际总 tokens / 成功链数`；成功数为 0 时为无穷。候选组相对 A 的成本比同时置信上界 ≤ 0.80（至少 20% 节省），并且工具+模型墙钟成本比上界 ≤ 1.10。不能只报告成功样本的便宜路径。
- 工具失败/误拒绝不超过 1%，不存在未修复的跨边界访问、漏账或 oracle 泄漏；纳入范围内可表达率 ≥ 90%，逃生路径 ≤ 5%。不支持任务按预登记规则进入覆盖和成功分母。
- 统计方案：配对任务链 cluster bootstrap（固定种子、10000 次，整链携带所有组/重复/步骤），对两项主比较的成功率差、回归差、token 比、墙钟比共 8 个判定量使用 Bonferroni 同时 95% 区间。若退化数据导致区间不可估，判 INCONCLUSIVE；不以点估计代替。小样本仅描述，不硬套此门。
- 确认样本数需在开测前用独立工程/探索方差做一次功效与精度计算，并锁定固定 N、最多请求数和停止时间；至少 30 条新独立任务链、每组每链 2 次重复只是最低设计条件，不能保证功效。预算无法支持锁定 N 时停止于 INCONCLUSIVE，不暗减 N 后宣称达到门槛。

若 B 达标而 C 不优于 B，应保留“传统代码 + 语义工具”结论，不把结果包装成 IR 胜利。若要为 IR 产品方向投入，除上述对 A 门槛外，C 相对 B 必须在新独立确认实验中满足同一成本/可靠性门槛（作为该实验预登记主比较）。

**立即停止**：任何凭证/网络/文件越界、信息泄漏、用量不可信、模型身份漂移、预算触顶或隔离失效。保留原始记录，剩余 NOTRUN；不自动重试、修题或切换服务。**研究停止**：完成锁定样本后无实质收益、成本抵消收益、无法排除超过 5pp 的可靠性损失，或工具接入要求改写大部分现有架构，则停止扩展。输出负结果/不确定性及工程资产；不能继续寻找能赢的任务或增加原语直到“成功”。

## 9. 产品阶段门槛

达到一次实验门槛最多允许提出下一次独立复验申请。考虑产品立项至少需要：

1. 两次按冻结协议执行的独立确认研究，使用不同、未看过的新任务链；其中一次由未参与接口开发的复核者复现。不能把同一套 24 槽重跑或同一 source 的 replay 算独立复验。若模型相同，结论明确限于该模型；跨模型外推另需同样的证据与授权。
2. 收益在 Create/Modify/Debug 及连续维护中保持，达到上节门槛且包含固定工具开发/维护成本的摊销。C 产品方向还需 C 对 B 的独立净收益证据。
3. A09、A12 的实证缺口闭合，隔离/资源限制/故障恢复/长回放与压力测试有可复现证据，两个独立维护者能修改工具且维持语义一致，升级/兼容成本有记录。
4. 说明适用范围、覆盖缺口、负结果、许可/Plan 限制和实际用户维护需求。所有新样本、模型、费用均另行批准；不得用商业产品路线反向放宽实验标准。

即便全部满足，也只形成“可考虑立项”的证据包。**产品开发、引擎接入、公开发布与预算仍需用户明确的新决定，不自动授权。**
