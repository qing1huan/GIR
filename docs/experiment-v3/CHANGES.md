# v3.0 与既有计划的差异

| 项目 | 既有计划/当前探索 | v3.0 决定 |
|---|---|---|
| 研究问题 | 结构化 IR 能否改善 AI 游戏编程 | 分别检查操作接口、语义表示与执行验证机制对 AI 开发和维护的影响 |
| 对照命名 | 原 Word 的 A=JS/TS、B=IR 文本、C=IR 语义 API；当前24槽只有 IR/JS 文本 | 新 A=JS+强分析；B=同一JS+语义查询/编辑；C=GameIR+匹配接口/验证。旧记录不改标签 |
| 工程方向 | 扩展 IR/表达能力的长期构想 | 维护当前架构，先复用现有运行时、编辑器和代码分析工具，做 M1 最薄接口可行性 |
| 基线强度 | 文本生成/零工具 | A 具有符号、引用、诊断、原生重构等正常能力；A/B 共享分析后端 |
| 证据单位 | 单次生成、固定用例观察 | 保留当前探索；未来以 Create→连续 Modify→Debug 的任务链为主单位 |
| 公平预算 | 当前输出上限相同，输入是 byte 估计，实际用量不等 | 新实验需要可信 token 预留、完整工具/反馈/修复总账；不能宣称旧批次严格总token匹配 |
| 归因 | IR 与 JS 的表示差异 | A/B 测接口增量，B/C 是表示+验证的组合；补最小消融但不夸大纯因果 |
| 产品入口 | 长期应用方向 | 固定数值标准、两次独立确认、维护/隔离证据后才考虑立项；仍需用户新决定 |

没有重写原始 Word、冻结材料、候选、测试或 oracle。当前架构冻结是维护性冻结；A09/A12 仍 NOTRUN。本轮新增模型请求 0，候选执行 0。24 槽的静态交接只准备之后的精确审批，不赋予执行权限。
